# Asterway V1 文档与代码复核及整改计划

日期：2026-11-05。范围：复核用户提供的《Asterway V1 功能缺口检查与全面业务测试验收文档》，对照当前代码、已验收设计和后续明确确认的规则，交付问题清单及整改计划。

本轮不修改业务代码、SQL 或前端，不操作数据库，不执行完整业务测试，不提交、推送或更新 V1 标签。本文及配套矩阵是本轮新增的审阅材料，原附件保留。

## 1. 结论

附件不能直接作为整改任务单：

- 原列四项 P0 中，任务完成不可重开、阶段必须支持 PAUSED、归档遇未结束执行的二选一，均与后续已确认基线不同；应先校正文档，不能据此回退代码。
- 阶段完成前置条件的代码观察部分成立，但“必须全部有效任务完成且所有暂停执行结束”的产品要求，没有在现行已验收基线中明确冻结；应作为规则补充决议，不能先认定 P0。
- 本轮静态确认一项 P1：看板当前目标包含未来目标。取消待生效时区后保留先前缩短的执行截止，符合现有接口文档的保守约定，列为待确认的策略改进，不计入已确认缺陷。
- 安排日期与执行资格、父级完成后的写入权限、是否强制先属周再入日，需要明确边界后再实施。这里有真实的代码行为差异，但不能把全部差异合并成一项已确认缺陷。
- 完整业务验收仍为 NOT_VERIFIED。“尚未执行完整测试”是验证状态，不等于相关功能没有实现，也不代表已证明没有其他缺陷。

附件九项结论见第 3 节；151 条原用例及 7 条综合流程的复核标记见 [用例复核矩阵](V1_验收用例复核矩阵.md)。矩阵不包含伪造的通过结果。

## 4. 确认问题与待确认策略

### C1：P1，看板当前目标未排除未来目标

**后续状态（2026-11-05）**：用户已批准本项修复，现已完成本地编码、打包和启动检查；业务用例仍未执行。整改详情见第 9 节，以下证据保留为 V1 原始问题记录。

**证据**

- backend/goal/src/main/resources/mapper/goal/GoalMapper.xml:43–46：CURRENT 分支要求开始日期不在未来。
- backend/dashboard/src/main/resources/mapper/dashboard/DashboardMapper.xml:110–133：goals 与 goalsCount 只按本人、未删除、未归档过滤，没有开始日期条件。
- backend/dashboard/src/main/java/com/asterway/dashboard/service/impl/DashboardServiceImpl.java:71–79：直接返回 Mapper 列表和总数，没有补充日期过滤。

**静态场景**：本人创建明天开始、未归档目标；普通目标 CURRENT 列表排除它，而 dashboard/goals 会返回它。即使没有阶段或任务，也能进入看板当前目标列表。此处是代码路径推导，本轮没有创建数据或调用业务接口实测。

**影响**：同一未来目标在当前列表和今日看板的口径不一致，对应附件 GOAL-003。不要把这个问题错误改成增加目标激活调度。

**修复建议**

1. 在看板 goals 和 goalsCount 两个查询同时使用账号当日日期，补齐开始日期为空或不晚于今天的筛选。
2. 不在前端对已分页结果再过滤，否则总数、页数和空页会不一致。
3. 这项只修未来开始口径；是否隐藏已完成但未归档目标是另一项展示决策，不顺便改变。
4. 另行核对未来目标被安排到今天的任务展示；安排是否允许见第 5 节。历史统计、历史执行和归档查询不能因此过滤掉真实历史。
5. 无需新表、DDL、环境变量或定时任务。

**后续定向核对**：开始日明天/今天/为空，账号时区切日，列表与 count 一致；不修改目标状态；已有历史投入不丢失。

### C2：策略待确认，取消待生效时区后仍保留原截止

**证据**

- frontend/src/views/ProfileView.vue:64–70：取消切换会提交当前有效时区。
- backend/identity/src/main/java/com/asterway/identity/service/impl/UserServiceImpl.java:320–331：清空 pendingTimeZone/effectiveAt 后调用 shortenBoundary，参数为 null。
- backend/execution/src/main/java/com/asterway/execution/service/impl/ExecutionSessionServiceImpl.java:712–724：null 直接返回，且只接受更早截止。
- backend/execution/src/main/resources/mapper/execution/ExecutionSegmentMapper.xml:28–32：更新仅允许缩短 eligible_until。
- docs/execution/后端业务与接口约定.md:72：明确约定修改待生效时区时同步更新开放段截止，“不延长已经确认的截止”；common 中立接口注释也采用同一规则。

**静态场景**

1. 周未定日任务运行中，原自然截止为下周一。
2. 设置待生效时区，开放段截止被缩短为旧时区次日零点。
3. 零点前取消时区切换，账户不再有待生效修改。
4. 开放段仍保留该零点截止，即使持续有效心跳，也会到点按 PLAN_BOUNDARY 暂停。

代码与现有接口文档一致，不能将这一现象直接归为实现缺陷。保留当前策略时，应明确取消动作只撤销账户时区修改，不恢复本段已确认的截止；到点暂停后可按当时资格重新恢复。若希望取消动作也消除对尚未到期运行段的影响，则属于对现有约定的调整，需要先明确预期。

**若决定调整策略，建议这样实现**

1. 将中立联动职责调整为按最新账户配置重算当前开放段边界，继续在用户锁和父事务内执行，不新增业务 Service/Controller 链。
2. 自然计划边界由当前有效安排及对应时区计算，再与实际仍待生效的时区边界取最早值；不要简单把旧 deadline 清空或改成无限。
3. 只对尚未到期、仍运行的开放段恢复合法未来截止；已结束段、已到期段及历史时间不延长、不重开。
4. 心跳超时仍独立封顶，不能因取消时区切换恢复已超时会话。
5. 日安排仍在本日结束暂停；取消时区切换不能绕过真实的日期或周边界。
6. 不需要新增表；沿用现有会话链、Mapper/XML 和 common 中立契约。

**后续定向核对**：先按当前策略验证取消后仍保留截止、到点暂停可重新恢复；若批准边界恢复，再验周未定日设置后取消、替换待生效时区、日安排真实午夜边界、取消前已超时、切换已经生效后再修改及历史段不变。

## 5. 需要集中决定的业务边界

以下是当前行为和附件要求的差异，不先伪装成已确认 P0。

| 决议 | 当前代码事实 | 建议 |
|---|---|---|
| R1：目标/阶段完成的前置条件 | 手动状态入口不要求全部有效任务完成；任务自身完成会拒绝任何未结束执行；父修改会使 RUNNING 失效时拒绝，但 PAUSED 可保留；通知确认另有全部有效任务完成条件 | 明确是否所有“完成”入口都必须达标、是否要求结束 PAUSED、空目标与空阶段如何处理。若采用强约束，在原 Service 主链统一校验，不能只隐藏按钮 |
| R2：父级已完成后允许哪些写操作 | 公共 writable scope 只禁止归档；可在已完成父下新增或重开任务，也能安排未完成任务，执行开始才拒绝已完成父链 | 若选择强生命周期，建议先显式重开父级，再新增/重开/安排；不要暗中重开父级。需同时考虑任务重开、增删与父状态的关系，不能只补“父完成时”一个 if |
| R3：先周后日是否强制两次业务操作 | assign 要求匹配的 weeklyPlanId/day，能够从无安排状态一次写入周和日；数据关系不孤立，但没有验证原安排已属于目标周 | 原开发文档使用“必须已经属于周”。需要明确是禁止孤立日安排，还是必须已有周安排。若强制后者，再为旧安排为空或属于其他周时加守卫，并处理跨周改期入口 |
| R4：计划日期与开始日期一致性 | 日计划不能在过去，但不比较任务/目标开始日；可接受一个到安排当天仍无法开始的任务；执行入口会再次拒绝 | 建议允许提前规划未来周/日，但目标日不得早于目标/任务开始日；周未定日只要求该周存在可执行日期。阶段日期仍仅作参考，不能擅自升级为硬限制 |

R1 与 R2 要一起决议：如果“父完成”只是当时的用户结论，之后允许调整与保留历史，则不应强行套持续不变量；如果要求完成父始终不能包含未完成任务，后续写入也必须受约束。

阶段 PAUSED 属于当前三状态之外的可选新增需求。若另行确认，需要先调整 stage.sql 的主体和历史状态 CHECK，提供既有库手工变更与隔离校验，SQL 验收后再改状态校验、执行资格、前端和对应验收项。不能只把 ctx.state 的布尔参数改一下就宣称完成，更不能连带让目标状态接受 PAUSED。

普通目标/任务创建目前没有统一幂等键契约。同名任务明确允许存在。附件 NFR-005 不应直接要求所有创建 POST 网络重试都自动去重；若需要这一能力，应先确认请求幂等标识与失败重试规则，不能用名称唯一替代。

## 6. 必须修正或补充的验收口径

1. TASK-010、FLOW-003 改为当前允许重开、旧完成历史不删除、再次完成动作累计而任务数去重；TASK-011 仍保留“未重开的已完成任务不能直接开始执行”。
2. TASK-006/007 区分任务状态和执行会话控制：影响运行资格的状态修改要求先暂停执行；把任务状态改为进行中不自动创建执行，更不能借状态权限绕过开始/恢复权限。
3. EXEC-003 明确另一任务开始返回 409，不隐式暂停原任务；同账户其他 SID 先暂停再恢复才能接管，重复恢复不能抢 SID。
4. EXEC-011/012、NFR-002 明确以最后心跳加九十秒和安排截止封顶；不能要求服务端知道浏览器实际断网时刻并把其后所有时间都计零。
5. GOAL-010、EXEC-013、FLOW-006 固定为 confirmed=true 的同事务归档流程；GOAL-013 明确旧删除接口返回 410，而不是只禁止物理删除。
6. HABIT-006/008/015 写清当天已经完成后保留 1/1；撤销后按最新规则判断，可能从今日清单退出；删除后禁止撤销；封存日不能改写。
7. SYS-002 明确角色分配、权限与菜单授权属于 SUPER_ADMIN；不能把普通 ADMIN 测成应当具备这些权限。
8. TASK-013 按当前不支持父级迁移处理，资料 DTO 不接受 stageId；不要为了让可选用例通过而新增迁移功能，改变既有历史归属。
9. GOAL-011/012 及阶段暂停用例不纳入当前必须通过项；如果需求新增，再恢复相应验收。UI 统一主题、换肤或全面重构只是可选增强，不是当前 MVP 缺口。
10. 统计的执行日期按查询时账号有效时区划分；打卡保留原 businessDate，段开始时区供追溯，不能把两者都要求成“历史日期永不变化”。
11. FLOW-004 的周一/周三不能直接套到任意真实当前日期；人工场景要参数化为合法的当天和未来日期，不因选择过去日期而误判系统。
12. “未执行”不得填成“失败”或“通过”。代码中的所属人、用户锁、部分唯一索引、历史追加、截止封顶是静态保护证据，仍需要后续运行验收。

另应补充：多个暂停会话、旧段心跳重放、开始接口实际恢复时的 resume 权限、后台轮询不续签七天登录、到期归一化不被失败命令回滚、取消时区后的已选边界策略、时区回拨封存日、总毫秒累计后再转秒。
