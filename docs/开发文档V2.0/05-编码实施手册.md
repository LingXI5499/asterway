## 一、编码前置条件

01～04 为本版设计输入，需求编号保持稳定。现有工程仅完成结构初始化；编写首个业务切片前，应先关闭 09 的 OPEN-001～005 中对应前置问题。需求评审、数据库执行、接口运行和业务验收分开记录，不因本文填充完成视为已确认或已通过。

仓库与工具 → 空库迁移及约束 → 后端公共机制 → 账户 → 目标阶段任务 → 周日安排 → 执行 → 完成与通知 → 生命周期 → 日期补偿 → 习惯 → 查询与后台 → 恢复 → 后端验收 → 页面原型 → 前端联调 → 系统验收与发布。

## 四、数据库初始化流程

### 4.1 初始化前确认

开发、测试、生产分别隔离数据库和角色。迁移角色可建表，运行角色不具备 DDL 权限；备份角色和账本权限独立。核验目标实例、UTF-8、时区、schema 和 btree_gist，pgvector 非本期业务依赖。所有设计关系无物理外键。

### 4.2 初始化步骤

1. 在隔离开发库确认连接目标和最小权限，不连接生产做开发测试。
2. 依据 A13 的展开字段和 A01 的约束编写下表迁移；按真实依赖排序。
3. 在应用配置中明确 app、session_store、migration_meta 的建模及 search_path/表名约定，先关闭 OPEN-002。
4. 只初始化护栏单例、两项配置和受控首次管理员，不写公开固定密码。
5. 以单次受控迁移任务执行全部所需迁移；不能只部署 V001 就开放注册，业务依赖 V006 的去重、事件和审计。
6. 在新空库、旧测试库升级、重复启动和失败恢复四种条件检查迁移。
7. 查询真实系统目录，核对字段、主键、唯一、CHECK、排除和索引，并确认全库物理外键数量为零。
8. 在真实 PostgreSQL 检查并发、回滚和无外键会话适配，不用内存数据库替代。

36 张设计表全部可从空库复现；公共字段不遗漏；物理外键为零；唯一及时间排除并发测试通过；框架会话实际事务的删属性再删父、写属性先锁父行为有证据；迁移失败不进入就绪状态。当前这些标准均未完成。

### 5.3 工程核验、构建与启动顺序

依次实现安全过滤链和响应空值策略、统一错误和 traceId、DTO 校验、账户锁、幂等及 outbox、受控时钟、框架会话适配、独立安全账本和启动恢复，再实现首条业务接口。


```powershell
# 在仓库根目录执行；先确认当前终端和 IDE 都使用 JDK 17
mvn --version
mvn -o -f backend/pom.xml validate
# 后续实施阶段：依赖齐备并新增测试后执行
mvn -f backend/pom.xml clean verify
# 只有迁移、配置和安全基础齐备才进行应用启动验收
mvn -f backend/pom.xml -pl app -am package
java -jar backend/app/target/app-0.1.0-SNAPSHOT.jar
```

本次在 2026-10-22 重跑离线 validate，父工程和 10 个子工程共 11 项均为 BUILD SUCCESS；它只检查工程模型。verify、package 和启动命令是后续实施步骤，不是本次已运行结果。不要从某个子工程单独 package 后就推断依赖已安装；从父 POM 使用 `-pl app -am` 才会把 app 所需的兄弟工程纳入同一次构建。不能用未准备的本地默认数据库连接去推断远程服务不可用。

### 5.4 后端初始化完成标准

聚合编译及适用测试通过；app 包含各模块 XML；迁移成功；身份、CSRF、越权和错误均可按真实 HTTP 验证；日志无秘密。当前仅 `validate` 已通过，不代表编译、打包或运行通过。
