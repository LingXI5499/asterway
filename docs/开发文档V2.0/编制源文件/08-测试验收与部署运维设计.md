## 1. 怎样使用这份设计

06 的每个 DEV 切片在写代码前先选本表相关 TEST，确定输入、前置数据与故障注入位置；写完后保存真实结果和证据。后端与接口验收后再做页面原型、前端实现和联调，最后完整验收。测试不能等所有代码都写完才开始。

用例采用 现行业务规则的业务规则。量化响应、负载、确认、备份及恢复数字沿用 NFR 和架构作为本版设计目标，保留原“建议基线”来源；没有实测就不能写“已达标”。本文的测试方法是工程细化，不改变业务规则。

测试执行后才填写执行人、日期、实际环境、构建版本、实际结果与证据路径。可用状态为 `NOT_VERIFIED`、`PASS`、`FAIL`、`BLOCKED`；`BLOCKED` 必须写出具体缺失条件。设计写完不自动变成 `PASS`，没有执行结果不填零错误或虚构耗时。

同一TEST含多层验证时，可追加子项，例如仓库并发、HTTP结果与浏览器反馈分别记录。后端阶段只验其适用部分，前端部分保留 `NOT_VERIFIED`；不能因局部通过就把完整TEST改为PASS，也不能要求未来页面先完成再开始后端。最终系统验收检查完整覆盖。

## 2. 环境、数据与证据

### 2.1 分层验证

| 层次 | 验证什么 | 主要证据 |
|---|---|---|
| 业务单元 | 状态、日期边界、延期公式、字符和统计口径 | 输入样本、断言结果、受控时间 |
| 真实 PostgreSQL 集成 | 无外键逻辑关联、唯一与排除、锁、回滚、提交、Mapper XML、框架清理 | 数据库版本、迁移版本、事务前后快照、并发时间线 |
| HTTP/安全 | 02—05契约、DTO/VO、HTTP、Cookie、CSRF、当前授权与幂等 | 脱敏请求响应、自动化报告、追踪标识 |
| 浏览器/端到端 | 登录到计划执行完成、控制页/观察页、空态、错误、只读和历史 | 浏览器版本、步骤、截图/录像及对应服务端事实 |
| 系统质量 | 参考负载、安全、资源竞争、启动恢复、备份、发布和回退 | 原始样本、监测曲线、故障日志、恢复清单与时间 |

不能用 H2 或纯内存结果证明 PostgreSQL 的约束和并发正确。Apifox/Postman 适合调试并保存请求结果，关键回归仍应能重复执行，不能只留一句“接口测过了”。

### 2.2 测试数据

至少准备普通用户 A/B、管理员、两个可用超级管理员；使用合成账户和正文，不使用生产密码或真实备份。测试覆盖未来目标、无任务目标、不同生命周期、未执行/部分执行/已完成任务、周内无日期任务、跨日区间、归档/删除历史和各类习惯节点。

日期测试固定可重放的时间与时区，覆盖上海、纽约夏令时起止、周日到周一、年末、时区生效和日期线导致当地日期重复。仅修改浏览器时间不能代替服务端受控时间；真实同步与时钟跳变另测。

性能数据采用 NFR：100 个账户、10 活跃账户、20,000 任务、200,000 专注区间、100,000 习惯日结果、三年历史；其中重度账户至少 100 目标、500 阶段、10,000 任务和100,000区间。这些是验证规模，不是产品配额。

## 4. 性能与计时时效怎样测

先预热5分钟，稳定负载5次业务请求/秒持续30分钟；查询/写入/历史统计按60%/30%/10%混合。10个计时任务的确认、登录哈希、滑动验证、页面刷新和后台工作另计流量与资源，不藏在业务请求数字之外。再做15次业务请求/秒、1分钟突发，并验证结束后2分钟内恢复。

每类关键请求至少200样本；列表按每页50条，历史分别查一年与三年。请求测试超时10秒；超时和失败保留在原始结果，不丢弃慢请求。浏览器首屏/导航各至少30样本；正常网络按NFR记录往返、带宽和故障条件。

| 指标 | 采用的设计目标 | 报告必须写清 |
|---|---|---|
| 普通查询/详情 | 服务端P95≤500毫秒 | 分类别，不用所有接口混合平均值代替 |
| 业务写入 | 服务端P95≤800毫秒 | 包含必要提交与跨对象联动，不只测单表 |
| 历史统计/认证 | 各P95≤2秒 | 一年/三年与有效/错误凭据分别报告，不降低哈希强度 |
| 页面 | 冷启动首屏P95≤4秒；导航/刷新/提交结果P95≤2秒 | 浏览器、网络、缓存、资源及主内容可用时刻 |
| 稳定失败率 | 技术失败≤0.5% | 预期业务拒绝另列，60分钟连续使用无不可恢复假死 |
| 执行确认 | 健康条件成功持久化间隔≤15秒 | 架构发送10秒、许可15秒、扫描5秒是初始工程值；不能只测发送次数 |
| 异常暂停 | 服务健康时T+45秒前保存，专注终点T | 时间线包含扫描、队列、锁与提交；停机按恢复门禁另测 |
| 时长准确性 | 已确认30分钟组合累计误差≤1秒 | 区分实时估计、最后确认值与最终值；受控时钟及实际同步均有证据 |
| 周期/通知 | 边界处理60秒、通知5秒、积压恢复5分钟 | 通知形成与页面显示分别记录，不能靠页面乐观提示假称已投递 |

当前全部 `NOT_VERIFIED`。失败后先定位查询、锁等待、连接、哈希、I/O或前端渲染；只优化有证据的瓶颈，不同时大改三层再猜原因。不能增加用户对象上限、删旧历史、关闭持久性或放宽业务条件来“过压测”。

## 5. 无外键完整性与会话适配验收

### 5.1 应用逻辑关联巡检

按01的关系目录分批检查：父身份存在、userId一致、目标—阶段—任务父链、周日同账户同周、安排唯一、执行与区间同任务、运行/开放段/控制指针一致、时区指针、习惯当前规则与星期集合、日结果规则归属、完成事实与任务状态、通知条件轮次及历史摘要。

运行时间为每日低峰、发布后、迁移后和恢复后。巡检使用有界只读查询与记录，不长期占账户命令锁；需要隔离或修复时另走受控事务并重验。发现异常记录对象和关系、隔离受影响写入并人工核对，不能自动删除孤立历史或将所有者“改成能连上”为止。

### 5.2 Spring Session无物理外键

框架两张表由未来Flyway迁移管理，关闭框架自动建表；保留兼容字段、主键和索引，去掉默认物理外键与级联。只去掉约束而继续默认依赖级联不算适配完成。

仓库删除/注销/过期清理在同一实际仓库事务锁父会话，显式删除属性再删除父；属性新增也在同一仓库事务锁并确认父存在。父删除与属性写入必须互相冲突串行，不能外层持锁、内层新事务等待自己。

TEST-056必须覆盖：父已不存在、父删除过程中写属性、并发保存、会话ID轮换、正常注销、过期清理、重复清理和旧对象迟到保存。核对没有孤立属性/死锁/权限复活，并以账号安全版本和恢复会话代次逐请求拒绝旧权限。框架适配是必要接入工作，不能另建一套平行业务会话库。

## 8. 备份、恢复与回退

### 8.1 备份链和RPO

采用每日物理基础备份、持续WAL归档、独立故障域存储。低写入归档推动初始不超过5分钟，给传输、重试和检测留出15分钟RPO余量。最终证据是连续可恢复点，不是“任务每五分钟启动”。`pg_dump`仅辅助，不能代替WAL恢复的基础备份。

30天恢复窗口连同依赖的更早基础备份、WAL、时间线和清单一起保留。配置、版本、密钥和恢复凭据另行受控；核对加密、权限、完整性、过期清理以及归档失败导致运行盘WAL积压。WAL切得越频繁，未填满段也可能增加独立空间，不把30天备份塞进40GiB运行盘估算。

### 8.2 独立安全核验

账本涵盖改密、改名、账户状态、角色及恢复会话代次。先保存独立意图，再同库事务保存安全变化/审计/待同步依据，提交后可靠同步结果；提交未知保持未决。独立账本不能只是本库 security_change 的另一张表。

恢复时核对完整性和覆盖水位。未决或凭据/标识版本落后则隔离相关账户；不能仅清会话或把版本改新后继续用旧密码哈希。依据缺失且无法界定影响范围时全部恢复账户拒绝登录与敏感授权。账本生命周期覆盖所有恢复点差异，不能按普通日志轮转删掉唯一撤销依据。

### 8.3 RTO与恢复门禁

按“故障检测响应 → 准备替代环境/材料 → 隔离恢复基础备份与WAL → 保持登录和写入关闭 → 换恢复代次并清理会话/属性 → 独立账本核验 → 遗留执行与周期补偿 → 全部逻辑关系/统计/核心读写检查 → 开放”执行。

内部演练预算为：响应15分钟、环境30分钟、恢复90分钟、安全与业务核验45分钟、核心验证开放30分钟、余量30分钟，合计240分钟。计时从核心服务故障开始，包含无人响应、取秘密、下载和安全隔离处置；安全未恢复不能先宣布达到4小时。

上线前、每月至少一次、重大迁移/存储变更后演练。记录恢复点与实际丢失范围、开始/结束时间、所用材料和每步耗时、旧凭据重放、执行截断、巡检结果及残余风险；目前均 `NOT_VERIFIED`。

### 8.4 不同失败选什么回退

| 情况 | 处置 |
|---|---|
| 应用变更失败，结构与新数据仍兼容旧包 | 可按验证过的条件回退固定应用产物，重新走启动/执行恢复门禁 |
| 数据结构或新语义不兼容旧包 | 保持停服/受控维护；追加兼容修正或隔离数据恢复，不能直接换旧包继续写 |
| 迁移失败 | 不就绪；保存迁移版本与日志，确定本次原子结果和恢复点，不手改历史为成功 |
| 运行盘损坏/错误数据需旧点恢复 | 隔离重建，使用完整独立链和安全核验流程；不是普通容器重启 |
| 安全账本或秘密缺失 | 保持对应隔离，报告真实阻塞和RTO影响，不放行旧身份凑指标 |
| 仅通知/统计展示故障 | 核心已保存结果继续成立；明确未加载/延迟，保留补偿和恢复依据 |

回退不会逆转“任务完成不可撤销”等业务规则。不得通过删卷、清库、删除永久事实、取消排除约束或开放所有权限作为默认修复手段。

## 9. 运行监测与缺陷处理

### 9.1 监测最小集合

每分钟探测入口、身份关键依赖、核心查询及受控写入；合成或回滚探测不改真实用户数据。连续两次失败进入故障，首次失败后5分钟内发到运维接收通道；备份可恢复点超过15分钟立即告警。恢复要求连续成功探测及核心读写通过，不能仅凭静态首页或进程存活。

观察请求分位数/失败率、锁等待、计时确认间隔、过期执行、队列和事件年龄、周期积压、连接/内存/CPU/磁盘/WAL、恢复点年龄。持续同一故障只在首次、影响升级和恢复时通知，不每轮刷屏；运维告警与用户目标通知分开。

运行日志建议30天、安全/后台审计建议90天，来源为NFR；长期业务事实、去重依据和安全核验检查点按各自保留要求，不能一起轮转。高频确认记录可聚合观测，不把完整请求逐条长期保存。99%月度可用性是运营目标，满自然月才有月度结果。
