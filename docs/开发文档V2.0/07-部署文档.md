# 07 部署文档

> 项目：Asterway · 个人成长管理
> 文档版本：V2.0　编制日期：2026-10-22　状态：设计审阅稿
> 工程基点：`27661335d458bc74294c6c3cc303649a175eddc9`；软件版本：`0.1.0-SNAPSHOT`。

> 适用目标：0.1.0-SNAPSHOT 的后续可发布构建；当前不是已部署系统。责任角色：发布维护者、验证者、数据库维护者，具体人员在发布前登记。

## 一、部署架构概览

浏览器 → HTTPS → Nginx（前端资源和同域 API）→ 单实例 Java 17 app → 受控远程 PostgreSQL 17.11；独立安全账本、基础备份与 WAL 归档分别保存。应用侧使用 Linux/Compose 的部署设计，数据库由既有远程主机管理。目前没有 Dockerfile、Compose、Nginx 配置或已登记域名，不能按现成生产环境描述。

### 2.2 环境隔离原则

三个环境使用不同数据库、会话和凭据。配置差异通过外置配置注入；生产默认拒绝缺失必需配置，禁止静默使用 local、本地回环 DB、空凭据或调试日志。任何数据修复有变更记录和恢复依据。

## 六、部署前检查

记录目标版本、环境、人员和窗口；适用测试和业务验收完成；审查全量迁移与新旧包兼容；确认独立恢复点、安全账本水位、秘密、域名/证书和告警；固定产物和摘要；核对单实例所有权、端口及网络；明确应用回退与数据库前向修复/恢复的选择。任一硬前置缺失不开放业务。

## 七、部署步骤

### 7.1 开发环境

按 05 使用固定开发分支并核对工具，准备隔离 DB，配置 ASTERWAY_DB_*，执行已审查迁移，构建启动 app 后再做账户/业务冒烟。frontend 尚不存在，不执行不存在的 npm 命令。默认 8088 来自配置，不是已监听端口的证明。

### 7.2 测试环境

使用固定构建和独立配置/数据库；完成扩展和 schema 核验 → 单次迁移 → 启动恢复 → 安全/身份冒烟 → 核心业务 → 06 的完整测试。保存提交、配置、依赖、迁移和测试证据，失败不提升到生产。

### 7.3 生产环境

当前尚无生产地址和可执行部署清单，本节为发布作业设计。发布维护者在完成部署文件和隔离验证后，按以下顺序执行，不临时猜测服务名或路径。

1. 进入维护状态，停止新命令，记录旧版本、配置、迁移和恢复点。
2. 确认独立备份链、账本覆盖及所需秘密可用。
3. 以迁移角色执行单次受控迁移；未就绪时不放流量。
4. 启动单实例 app，核验新运行代次；处理遗留执行及必要周期。
5. 加载经过校验的静态资源和 Nginx 配置；先配置校验再重载。
6. 验证安全、个人隔离、核心读写、历史和逻辑关联。
7. 开放流量后观察错误率、耗时、执行确认、事件水位和恢复点。
8. 记录实际结果；触发回退时执行第九节，不将容器重启当作数据恢复。

## 九、回滚方案

### 9.1 回滚触发条件

核心链路不可用、越权或撤销失效、数据一致性破坏、无法维持单实例/单计时、迁移失败或恢复依据失效时立即停止继续放量。质量阈值以 02 为准，发布窗口观察和样本不足时不能声称整体达标。

### 9.2 回滚步骤

先保留日志、版本、traceId 和受影响范围，冻结新命令。结构及新数据与旧包兼容时回退固定 app/静态包及匹配配置，并重新通过启动恢复和冒烟。结构不兼容时保持维护，追加兼容迁移或执行已演练的隔离恢复；不执行临时反向 SQL 或改写 Flyway 历史。数据回退必须核对独立安全账本，作废旧会话/许可，不能恢复失效密码和权限。恢复后复验核心和历史并记录实际损失。
