## 一、日常运维职责

| 事项 | 角色 | 频率/触发 | 记录 |
|---|---|---|---|
| 可用性与就绪 | 应用维护 | 持续探测，失败触发 | 运行记录/事件单 |
| 日志、错误、执行和 outbox | 应用维护 | 持续指标，每日审阅 | 脱敏 traceId 与水位 |
| 容量、连接、锁与长查询 | 数据库维护 | 每日及资源异常 | 数据库运行记录 |
| 独立备份/WAL/账本 | 数据库与安全维护 | 持续水位；每日链完整性 | 备份清单和覆盖证明 |
| 恢复演练 | 应用/数据库/测试 | 上线前、每月至少一次、重大变更后 | 隔离恢复报告 |
| 证书/域名/依赖 | 发布维护 | 每周检查及到期预警 | 版本与有效期清单 |
| 权限和秘密 | 授权维护 | 人员/权限变化及风险触发 | 安全变更记录 |
| 依赖版本 | 开发维护 | 版本变更时 | CR、兼容测试与依赖树 |

监测至少包括身份失败/越权、业务失败及未知结果、锁等待、执行确认/旧代次拒绝、到期补偿、outbox 认领重试、磁盘/WAL、数据库连接、恢复点及安全账本覆盖。具体监测工具和接收渠道尚未建设，不在当前版本宣称已告警。

## 二、Bug 处理流程

### 2.1 总体流程

发现 → 登记 BUG → 评估影响和严重级别 → 先止损并保全证据 → 隔离复现与定位 → 修复/缓解/回退 → 评审及回归 → 按 07 发布 → 原环境复验 → 关闭与必要复盘。

### 2.2 Bug 登记规范

登记编号、标题、时间/环境、发现者、级别、受影响用户/功能/数据、FR/API、commit/配置/迁移版本、从初始状态开始的步骤、预期与实际、脱敏日志/traceId、临时措施、根因、修复方案/版本、回归证据和关闭结论。没有真实发生的故障不预填成已处理 BUG。

### 2.3 严重级别

| 级别 | 判断 | 处置 |
|---|---|---|
| S1 | 核心不可用、权限泄漏、重大数据损坏 | 立即止损、冻结危险入口，启动负责人响应 |
| S2 | 核心流程受阻或较大范围异常 | 优先定位，明确负责人及恢复步骤 |
| S3 | 局部功能异常且有替代路径 | 排入近期修复并回归相关链路 |
| S4 | 轻微文案或展示 | 常规维护 |

严重级别按影响而非修复难度；目前未承诺未经确认的 7×24 值守响应时限。

### 2.4 Bug 处理步骤

1. 固定现场版本、用户范围、业务日和请求链；日志脱敏。
2. 检查前端请求/旧状态、接口认证/CSRF/参数、应用事务/锁、Mapper 条件、数据库约束、配置和外部账本。
3. 在隔离环境按原步骤复现，定位根因；结果未知先查原意图，不重复写入。
4. 在现有 `feature/LingXI-develop` 修复并关联 BUG/FR/API，补充能复现原问题的回归用例；不另建 fix 分支。完成后先审阅，明确批准再推 feature；main 合入独立审批。
5. 对影响数据的修复明确查询范围、前后快照、备份与恢复，取得相应执行授权后实施。
6. 通过适用测试及评审再发布；原环境复验、观察并记录关闭依据。

### 2.5 Bug 处理决策

实现偏离既有设计属于缺陷；设计矛盾先修订设计；新增业务能力走 CR。环境故障按配置和设施处理，不能加无关代码。真实数据疑似受损时先隔离和核实，不默认删除或重建历史。

## 三、需求变更流程

### 3.1 总体流程

提出 → 登记 CR → 分类澄清/设计修正/范围改变 → 影响分析 → 成本风险及兼容评估 → 有权角色决策 → 更新需求与设计 → 编码测试 → 发布验收 → 关闭。

### 3.2 变更申请规范

记录 CR 编号、标题、提出人/日期、原因、当前/期望行为、价值和紧急性、SCN/FR、可观察验收标准及期望时间。首个实际申请从 CR-001 开始，历史 CHG 编号继续保留，不重新分配给另一事项。

### 3.3 影响分析清单

| 对象 | 具体检查 | 更新落点 | 兼容风险 |
|---|---|---|---|
| 场景/需求 | 原目标与新行为 | 01/02、SCN/FR/NFR | 新增范围与验收 |
| 架构/模块 | 数据所有权和依赖 | 03/04、MOD | 是否破坏单体和无环 |
| 状态/日期 | 允许转移、冻结日期、历史 | 模块业务逻辑/A07 | 旧事实不得重算 |
| 数据库 | 字段/约束/索引/旧数据 | A01/A13/迁移 | 扩展式兼容，破坏性变更需恢复 |
| API/类 | 路径、字段、null、枚举、错误 | 模块接口/类、A02～05 | 前后端部署顺序 |
| 测试 | 正常/异常/并发/恢复 | 06、TC/TEST | 回归范围和原始证据 |
| 部署/运维 | 配置、版本、恢复点和告警 | 07/08、REL | 旧包兼容和操作权限 |

### 3.4 变更实施规则

先分类、分析和决定范围，再同步文档实施。紧急止损可先缓解，事后补齐记录。新增编号不复用废弃编号；已应用迁移追加修正，不改历史文件；接口按兼容过渡和发布顺序推进；质量门槛变化不能用于掩盖失败。

### 3.5 变更状态

新建 → 分析中 → 待批准 → 已批准 → 开发中 → 待验收 → 已关闭；拒绝或延期记录原因和重新评估条件。没有批准的新增范围不纳入本期实现承诺。

## 四、常见问题排查记录

| 现象 | 先检查 | 证据 | 动作 | 现状 |
|---|---|---|---|---|

## 五、备份与恢复约定

备份对象为远程 PostgreSQL 的完整基础备份、连续 WAL、时间线和清单；应用产物、配置、必要秘密和独立安全账本分别受控。每日物理基础备份，低写入 WAL 归档推动初始不超过 5 分钟；保留至少 30 天恢复窗口及其依赖的更早基础备份。独立故障域、加密、最小权限和完整性水位必须验证，不能只同盘另存。

目标 RPO≤15 分钟、RTO≤4 小时，继承质量设计，尚未实测。最近一次恢复演练：尚无记录。恢复从故障开始计时，包含响应、取秘密、替代环境和安全核验，不因数据库恢复结束就停止计时。

恢复流程：隔离入口 → 核验基础备份/WAL/清单 → 恢复到选定点 → 换恢复与运行代次、作废旧会话和许可 → 核对独立安全账本及撤销差异 → 按最后可信点暂停遗留执行 → 按时间补偿周期 → 全逻辑关联、历史统计和核心读写检查 → 验收后开放。无法核实安全依据时保持对应账户隔离；不能将旧哈希或旧权限直接作为有效状态。

当前尚无备份任务、恢复脚本、账本服务和演练结果。A10 提供具体故障条件和证据要求；实施后保留真实命令、资源、耗时、恢复点及结果。
