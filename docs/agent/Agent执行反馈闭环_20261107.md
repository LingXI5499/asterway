完成范围包括统一的全局成长助手入口、可调宽导航与方案面板、连续对话澄清与规划、用户确认后的真实业务创建，以及执行反馈、复盘、可确认调整、原任务改期和进度跟踪。执行和打卡由用户实际完成；方案提交成功与目标完成分别展示。

## 1. 本轮补齐的五个缺口

### 1.1 查询编排与预算（减少普通概览查询耗尽预算）

- 新增 `agent/app/services/tool_budget.py`：每轮只读查询使用独立 `ReadBudget`，默认可执行 12 次、最多 5 轮（原 6 次/3 轮），并支持**本轮结果复用**：同一工具同一参数重复调用直接返回“复用本轮已核对结果”，不占额度。
- 提示词每轮附明确预算提示（剩余次数/轮次、优先 `get_goal_roadmap` 合并读取、分页或部分失败必须说明范围、未核对范围不得声称完整）。
- 规划整理与复盘各自有**独立操作机会**（`prepare_growth_plan` / `review_growth_progress` 不占只读查询额度），复杂问题不会再因为查询额度耗尽而无法进入规划。
- 新增 `get_goal_roadmap` 工具（目标→阶段→任务一次读取），减少“列表 + 多次详情”的连贯查询；读取仍走 Java 权限复核和路径白名单。
- 查询到上限时由工具服务返回“部分结果 + 尚未查询范围”，要求模型如实说明未覆盖范围，不再用编造内容补齐。

### 1.2 完整计划调整（改期不再只支持同周未定日）

Java 原子提交已支持复用原对象调整既有安排，保留任务与历史：

- 跨周改期：把已有任务从一周移到另一周（自动取/建目标周计划与日计划）；
- 已定日期之间改期：任意两个日期之间移动，不必先退回“未定日”；
- 保留原任务：只更新 `task_assignment` 指向的计划与日期，不复制任务、不改任务标题/归属；
- 保留安排历史：旧安排记录保留，新安排带版本；快照携带 `assignmentId/assignmentVersion` 做乐观校验，版本不一致整批回滚；
- 提交快照新增 `previousBusinessDate`（原安排日期）与 `reason`（改期原因），确认前即可在卡片上核对“改期前后 + 原因”；
- 运行中的执行计时会阻止改期并返回可读原因（不再笼统报“规划提交失败”）。

### 1.3 反馈驱动调整（复盘 → 可审阅调整草案 → 确认 → 更新原计划）

- 新增对话工具 `review_growth_progress`：按账号时区计算周期（本周/上周/最近 7 天/自定义），读取真实统计生成复盘，写入 `agent.review_report`，通过 SSE `review_update` 在右侧实时展示进度与结果。
- 复盘事实中固化 `facts.trackedPlan`：包含本次方案关联目标/阶段/任务/周计划/日计划/习惯的真实状态、完成数、逾期信号；复盘内容必须以这些事实为依据。
- 新增 `POST /agent/reviews/{id}/proposals`：据**已完成**复盘生成调整草案；限制同一复盘重复生成返回同一运行（幂等），旧对话/旧版本不会覆盖当前方案。
- 调整草案只生成“改期/安排”内容，复用已有任务与安排版本，**不复制任务、不自动确认**；右侧卡片展示每个任务的原日期、新日期与原因。
- 用户点击“接受并更新安排”后复用既有确认 + LangGraph 持久化 + Java 原子幂等提交，成功后右侧进度按真实业务记录刷新；重复执行返回同一提交回执，不会二次移动任务。

### 1.4 统一完成进度（右侧面板跟踪真实进度）

- 新增 `workflow_progress_service` 与 `GET /agent/planning/proposals/{id}/progress`：
  - 按提交回执 + 快照收集目标、阶段、任务、周计划、日计划、习惯 ID 并逐个读取真实业务状态；
  - 任务显示完成状态、逾期信号（超过截止/原安排日期）；周/日计划显示任务总数、完成数、逾期数；习惯显示今日应做与打卡状态；
  - 目标/阶段从所属关系向上补全，连“单独创建任务”或“只更新安排”的方案也能追踪其父目标；
  - 并发受限、部分读取失败会标记 `partial` 与“部分业务进度暂未读取成功”，不把未读取当成不存在；分页对象会提示“已加载范围”。
- 前端 `AgentActualProgress.vue` 渲染在右侧“方案与进度”面板：跟踪任务完成 x/y、逾期提示、目标/阶段完成率、计划与今日习惯状态。
- 进度与复盘右侧实时更新；方案卡片、回执、处理记录与业务页面链接并存。

### 1.5 失败恢复与完整链路验收

- 新增 `background_recovery.retry_memory` 与 `POST /agent/runs/tasks/{id}/retry`：仅本人、仅失败的记忆类任务可恢复；校验来源对话轮次/记忆仍可用；保留原失败审计记录，重新入队成功后才算恢复；连续失败 10 次给出明确提示；重复点击返回同一后续任务（幂等）。
- 前端运行记录页在“后台任务”标签为 `MEMORY_EXTRACT/MEMORY_EMBEDDING` 的失败任务显示“重新处理”，处理中自动刷新。
- 记忆抽取提示词包含字面量 `json` 以满足 DeepSeek `json_object` 要求，历史失败任务的重试实际处理成功（开发库任务 `SUCCEEDED`）。
- 本轮同时修复：
  - **Java 业务异常透传**：`java_client` 对 4xx/5xx 优先使用 Java 返回的中文业务原因（长度/控制字符过滤），改期被计时占用等原因能直接显示给用户，不再统一显示“业务状态已变化”；
  - **规划输出预算与轮次预算**：规划输出预算从 4096 提高到 8192，并在截断重试时使用更严格的精简/去重/字段约束；单轮对话预算从 120s 提高到 240s，Java 代理超时同步提高，覆盖“对话 + 查询 + 方案生成”的完整工具链，避免同一长方案反复截断或超时；
  - 聊天输入需求后，模型可自主调用 `prepare_growth_plan` 在右侧持续澄清与生成方案，不再依赖单独“制定方案”入口。

## 6. 后续体验发现的模型服务异常

2026-11-07 后续体验中，模型接口在首个输出之前返回 HTTP 500 / `InternalServerError`。该轮上下文读取成功，但模型请求约 17 秒后失败；没有执行工具或生成规划运行。使用合成的七个长期目标请求，以及不带工具的最简连接请求，均复现相同 HTTP 500。因此本次证据指向上游模型接口异常，不能据此认定多目标输入或规划结构有误，也不能把本地健康检查通过等同于模型可用。

- 修正应用的错误分类：上游 5xx 返回 `LLM_UPSTREAM_ERROR`，页面明确提示“模型服务暂时异常，未能完成本轮回复，请稍后重试”。鉴权、限流、参数、连接、超时和本地异常保持分别处理。
- 日志补充上游 HTTP 状态及安全分类，调用记录区分实际失败原因；不写入上游响应正文、请求内容或凭据。
- 保留手动重试，不自动重复发送模型请求或执行规划工具。流式中途失败仍保留已经收到的内容，轮次记录为失败，不能报告创建成功。
- 新增 12 项故障回归检查，覆盖错误分类、日志脱敏、调用记录、流中断和对话 SSE 失败终态；Python 全量 **40/40 PASS**，ruff 与 compileall 通过。前述 93 项是此前时点的验收记录，不能作为外部服务持续可用的保证。
