### 1.1 成长复盘生成不完整修复（原唯一 HTTP 失败项）
- 复盘生成使用独立输出预算 `AGENT_REVIEW_MAX_OUTPUT_TOKENS=4096`（原共用 2048 易被截断），并在任务内自动重试 `AGENT_REVIEW_MAX_ATTEMPTS=2`；仍不完整才置失败，不再偶发误报“复盘未完整生成”。
- 只登记 `finish_reason`、完成 token 数和尝试次数，不写正文、密钥或上游响应原文。
- 失败复盘可原地重新生成：新增内部 `POST /internal/agent/reviews/{id}/retry` 与公开 `POST /asterway/agent/reviews/{id}/retry`；只有 `FAILED` 可重试，`READY/PENDING/RUNNING` 返回 409。
- 后台任务超时回收：超过最大尝试次数的任务置 `FAILED` 后同步把复盘状态补齐为 `FAILED`（不再永久停留“分析中”）；未超限则退回 `PENDING` 由单 worker 重跑。
- 按用户限流：窗口 `AGENT_REVIEW_RATE_LIMIT_SECONDS=3600` 内最多 `AGENT_REVIEW_RATE_LIMIT_COUNT=6` 个复盘生成任务，超出返回 429（公开层映射为 `AGENT_RATE_LIMIT`）。
- 复盘页新增“重新生成复盘”按钮与失败提示；同区间失败后再点“生成复盘”复用失败记录并刷新统计快照，不重复建行。

### 1.8 聊天“无法录入”误解修复（用户反馈）

- 用户反馈截图中的回答（“没有创建、修改或安排的接口”）是旧系统提示词只描述了只读工具、没有说明录入入口造成的误会。已更新 `agent/app/llm/prompts/conversation.py`：明确要求模型在用户要新建/调整/安排时，引导用户查看助手回复下方的【生成成长方案】按钮，说明“生成方案→用户确认→业务服务一次性原子创建”，不得否认系统有经确认后的录入能力，也不得声称已创建。

### 1.9 规划生成 502、结构校验失败与记忆抽取失败修复（第三轮用户反馈）
- 现象：方案生成失败时界面显示“对话服务暂时不可用，请稍后重试”；用户的问题“学会 JavaSE，每天两小时，参考 Java 文档/知识库”无法生成，Python 日志为 `POST /internal/agent/planning/proposals 502`。
- 根因一：方案生成共用聊天输出预算 2048，长方案被模型截断（`finish_reason=length`），旧代码直接判失败。已新增 `AGENT_PLANNING_MAX_OUTPUT_TOKENS=4096`，截断时自动追加“精简方案（最多 3 阶段/8 任务）”约束重试；仍超限返回可操作的 422 `PLAN_GENERATION_TOO_LONG`（“方案内容超出输出上限，请缩小规划范围或分阶段生成”），不再笼统报“对话服务不可用”。实测同一长需求：第 1 次 length(4096) → 精简重试后 stop(1918)，成功生成目标+3 阶段+8 任务并进入“待确认”。
- 根因二：普通聊天触发的 `MEMORY_EXTRACT` 后台任务失败（`TASK_FAILED`/400 BadRequest）。原因是 DeepSeek `json_object` 模式要求提示词包含字面量“json”，旧记忆抽取提示词不含该词。已在提示词中明确“返回一个合法 json 对象”，实测同一路径任务转为 `SUCCEEDED`。
- 根因三：Java 代理把 Python 5xx 统一映射为“对话服务暂时不可用”。已改为 400/422/500/502 透传 Python 的 code 与中文 message（限制长度/字符集），界面可直接显示具体可操作原因；401/403/404 仍统一处理。
- 根因四：模型偶尔输出未通过方案结构校验（如把目标方案生成成日计划结构），旧代码只试一次就报“方案结构校验失败”。已把 JSON 解析/结构校验失败也纳入重试：最多 3 次，每次把具体校验原因和固定结构要求回传模型，仍失败返回可操作的 422；同时修正意图识别优先级（含“目标/阶段/任务/计划”的需求优先判为目标等成长对象，避免“每天投入两小时达目标”被误判为习惯/日计划）。
- 根因五（开发库特有）：Java 角色 `asterway_dev` 缺少 agent schema 的 USAGE 与 `workflow_run/plan_version` 的 UPDATE 权限，确认创建时 `FOR UPDATE` 行锁定失败，被归为 BadSqlGrammar/“规划提交失败”。已在开发库初始化脚本中补充授权并重新核对。
- 附带修复：方案卡生成期间先清空旧方案展示，并给方案详情刷新加请求序号守卫，避免旧运行覆盖新结果。
- 证据：`fix-verification-round3.md`、`dev-confirm-create-evidence.json`。
