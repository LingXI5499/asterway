## 三、发现的问题与必要整改

### 问题：断连/取消清理事务可能违反时间约束，轮次停留在 RUNNING

**现象**：页面断连（以及偶发的取消）后，服务端终态清理事务报 `IntegrityError`：

- `ck_agent_message_time`：`updated_at < created_at`；
- `ck_agent_turn_time`：`finished_at/updated_at < started_at`；
- 清理事务回滚导致轮次停留在 RUNNING，后续提问返回 409 `TURN_RUNNING`，直到截止时间归一为失败。

**定位**：PostgreSQL 的 `CURRENT_TIMESTAMP/now()` 是**事务开始时间**。清理事务先开始，再等待会话行锁；等生成事务提交后，它用陈旧的事务开始时间更新行时间，可能早于该事务提交前写入的 `created_at/started_at`。本机 WSL 时钟还存在周期性回拨，进一步放大了该问题。原始证据保存在本机未跟踪目录（PostgreSQL 错误日志与修复前源码快照）。

**修复**：仅修改 Python 持久化代码，**SQL 表结构和约束未改**：

| 文件 | 调整 |
|---|---|
| `agent/app/repositories/turn_repository.py` | 新增 `_now()`：`GREATEST(clock_timestamp(), started_at)`；`finalize`、`cancel`、`expire_running` 的 `finished_at/updated_at` 使用它 |
| `agent/app/repositories/message_repository.py` | 新增 `_now()`/`_conversation_now()`；消息 `updated_at` 与会话 `last_message_at/updated_at` 使用带行时间下限的数据库执行时间 |
| `agent/app/repositories/conversation_repository.py` | 摘要更新使用带 `created_at` 下限的执行时间 |
| `agent/app/services/conversation_service.py`、`turn_service.py` | 会话更新时间统一使用带 `created_at` 下限的执行时间 |

**回归**：修复后 P1.3.1 端到端 21 项全部通过，断连轮次正常 `CANCELLED`、可继续提问；P1.3.2a 开发完成后再次回归 P1.3.1 端到端仍 21 项全部通过；数据库中时间约束违反记录为 0。
