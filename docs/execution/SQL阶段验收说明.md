## 2. 两张表的职责和关系

关系为 `task → execution_session → execution_segment`；时间段另外逻辑关联本段使用的 `task_assignment`。

- **execution_session**：一次完整执行。保存所属用户、任务、首次开始、最终结束、状态、控制端登录 SID、最近心跳、结束原因和控制版本。
- **execution_segment**：一次连续实际执行。每次开始／继续新增一段；保存当时安排、段序号、开始／停止时间、结束原因、资格截止时间、时区和超时阈值快照。
- 暂停间隔不建段、不计时。暂停后直接结束，只更新会话，不新增时间段。
- 改期保留旧安排，恢复产生的新段引用新安排；旧段不会跟随任务当前安排改变。
- 实际耗时、暂停次数和当前段开始时间均从时间段计算，不重复持久化。
- 执行历史不设置逻辑删除列，也不提供业务删除、补录时间和耗时修正接口。任务、阶段、目标的逻辑删除／归档不删除执行事实。

详细字段类型和中文职责说明直接见 `execution.sql`，避免维护另一份不同步的建表定义。时间列统一为 `timestamptz(3)`，标识为数据库生成的 `bigint`。

## 3. 状态和约束

会话状态：`RUNNING → PAUSED / FINISHED`，`PAUSED → RUNNING / FINISHED`。`FINISHED` 是终态。

数据库保证四项业务唯一性：

1. 一个用户最多一条运行会话。
2. 一个用户、一个任务最多一条未结束会话，运行和暂停一并互斥。
3. 一个会话最多一个开放时间段。
4. 一个会话的时间段序号唯一。

数据库还检查：

- 运行状态必须保存非空白控制端 SID；暂停、结束状态清空控制端。
- 结束时间、结束原因和会话状态一致；心跳不能早于首次开始，最终结束不能早于最后心跳。
- 段结束时间和原因成对；结束时间不早于段开始、不晚于资格截止时间。
- 时间必须有限，截止时间必须晚于开始时间；序号、引用标识、超时秒数为正，版本非负。

以下规则由后续 Service 事务保证，不能声称 SQL 已经实现：

| 规则 | 后续实现职责 |
|---|---|
| 用户和父链归属 | 认证取得用户，校验任务、阶段、目标和安排同属本人；所有读写限定 owner |
| 普通用户专属 | 管理身份优先于保留的 USER 基础角色；限制必须先于超级管理员通行逻辑 |
| 当前可执行资格 | 有效本周安排、今日日期、开始日期、父链状态以及账号有效时区 |
| 状态与时间段对应 | RUNNING 恰好一段开放；PAUSED/FINISHED 没有开放段；段不重叠、序号连续 |
| 终态与历史保护 | 不恢复已结束会话，不改历史段，不接受客户端时间 |
| 登录 SID | SID 必须来自认证上下文，属于当前用户和当前有效登录会话 |
| IANA 时区 | 用项目现有可用时区校验；SQL 的非空白检查不是 IANA 验证 |
| 并发与控制版本 | 用户行锁、控制版本比较、旧段心跳拦截和重复请求处理 |
| 业务联动 | 任务完成／删除、调整计划、目标归档及登录撤销加入正确事务 |

## 4. 计时口径

- 开放段结束点为 `min(服务端当前时间, 最后心跳 + 本段超时秒数, eligible_until)`。
- 默认心跳 20 秒、超时 90 秒、扫描 15 秒；这些应用配置将在后端阶段写入现有本地 YAML，不在 SQL 新建配置表。
- 先按毫秒累加所有有效段，再统一向下取整为秒，不能逐段取整后累加。
- 查询日期按账号查询时有效时区转换成 `[当地起日零点, 当地止日次日零点)`；逐段计算交集，不把跨日执行全计入开始日。
- 使用日历日期和时区规则求零点，不使用固定 86400 秒表达所有当地日期。
- 时间段引用旧安排、旧任务的历史数据时，不套用当前有效对象过滤条件。历史实际投入与当前任务完成进度是两个口径。

## 5. 权限和菜单初始化

在 `identity.sql` 中新增独立标记块，不改写原有账户、角色或成长初始化段。新库可随完整初始化执行；已有库仅选取新增标记块，放入手工事务执行，不能重跑建表部分。

| 阶段 | 手工事务标记 | 效果 |
|---|---|---|
| 当前 SQL 准备 | 两个标记缺省或为 false | 登记七个禁用权限、六个隐藏禁用菜单，关联 USER；目标旧删除动作保持原状 |
| 后端完成并验收 | `asterway.execution_backend_ready = true` | 启用执行权限和菜单节点；页面继续隐藏；停用目标删除权限及按钮并移除旧授权 |
| 前端完成并验收 | 两个标记均为 true | 开放执行页面，按钮节点继续作为隐藏动作节点 |

这两个标记仅用于手工 SQL 的 `SET LOCAL`，不是环境变量、应用配置或新增系统配置。前端就绪而后端未就绪会报错。准备片段重复执行不会关闭已经完成的功能；同阶段重复执行不会无故推进角色、权限、菜单版本。

七个权限为 `execution:session:list/read/start/pause/resume/finish/heartbeat`。默认只关联 USER；片段会移除 ADMIN/SUPER_ADMIN 上误加的执行授权。**账户同时拥有 USER 和管理角色时，仍须依靠后端有效权限过滤和业务身份检查，单靠 SQL 角色授权不能完成这一限制。**

预留一个隐藏入口：`growth_executions`，路径 `/execution`，组件键 `execution/index`；只登记菜单，不代表已经确定或实现前端页面数量。心跳没有独立按钮。后续前端页面和交互仍单独确认。

片段遇到同名自定义／已删除权限或菜单、菜单结构不符时失败，不覆盖这些对象。目标旧权限和菜单只停用，保留字典记录及历史审计。

## 6. 已执行复核及复现方法

执行入口：

```powershell
./scripts/review_execution_sql.ps1
```

使用现有本地 Ubuntu 中的 PostgreSQL 17.11、Python 和 psycopg2；脚本不安装依赖或修改服务配置。所有连接固定指向专用 SQL 校验库 `asterway_identity_test`。

- 主检查：随机 schema 中装载原始六份业务 SQL，检查表结构、行内约束、唯一性、关键查询和三阶段授权；最终回滚整个事务，确认 schema 不存在。
- 并发检查：另一个随机 schema 中执行四项双连接真实索引竞争，第三连接观察锁等待。竞争赢家只在该临时 schema 内提交，另一连接必须得到指定唯一索引的 `23505`；结束后移除该 schema 并确认清理。
- 现有 `public` 对象和数据不清理、不重建，开发库 `asterway_dev` 不连接、不部署。
- 结果文件保存实际时间、数据库版本、全部检查名称、源 SQL 及复核脚本 SHA256。修改相关文件后需重新复核，不能沿用旧哈希的通过结论。

本次 **74/74** 通过，包括：三段执行 70 分钟、两段半秒合计一秒、暂停后结束不增加耗时、超时按最后心跳封顶、资格边界先于心跳截止、跨日各计十分钟、纽约夏令时 23／25 小时日期、改期保留旧引用、归档／任务删除后保留历史、权限阶段和幂等、四项并发唯一性，以及查询文档中两个参数化原型的实际执行。

这不是 Service、认证、HTTP 或界面验收，没有新增或执行 Java 单元、系统、集成测试。
