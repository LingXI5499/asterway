## 3. 模块划分原则

1. 按业务职责划分，先解释“谁负责什么”；代码包、Maven 模块、进程和部署单元在架构及代码结构阶段确定。
2. 每类业务事实有明确的数据所有者。其他模块通过约定能力使用它，不能各自维护一套相互矛盾的状态。
3. 目标、阶段、任务关系紧密，归入同一个业务模块并保留三个子模块；周计划、日计划归入计划安排模块。
4. 计划安排和真实执行分别负责。迁移当前安排不复制任务、不抹去已经发生的投入。
5. 看板和历史统计汇总事实；业务状态变更由所属模块负责。日期补偿先执行所属业务用例，再查询结果。
6. 永久业务历史由对应业务模块负责，不能仅依赖会轮转清理的运行日志或安全审计日志。

### 4.1 目标与任务的三个子模块

| 子模块 | 负责范围 | 必须保持的边界 |
|---|---|---|
| 目标 | 日期、自动开始与延期、归档与恢复、确认结束、重新打开及结束快照 | 目标不提供删除；无任务不触发完成；进度 100% 仍须用户确认结束 |
| 阶段 | 创建、修改、手动排序、暂停、恢复、完成、重新打开及空阶段删除 | 存在当前有效未完成任务时不能完成阶段；删除后仍保留必要历史归属 |
| 任务 | 创建、修改、优先级与预计耗时、业务状态、完成和符合条件的删除 | 必须隶属阶段；加入计划才具备执行条件；完成后不可恢复为未完成 |

当前进度按有效任务集合计算，删除任务退出当前考核；已经发生的完成事实和实际投入仍保留历史贡献。任务进度、专注耗时和预计耗时分别表达。

### 4.2 计划与执行的职责分界

计划模块回答“安排在哪个周期、是否指定某天、当前是否具备安排资格”；执行模块回答“什么时候实际执行、暂停了多久、有效投入是多少”。任务是否完成由目标与任务模块负责。

同一用户同一周只有一份逻辑周计划，周一至周日固定；日计划是周内指定日期的安排。是否单独建立日计划物理表，留到数据库设计决定。

同一账户最多一个任务正在计时，允许多个任务暂停；切换任务时，暂停原任务后再开始或恢复新任务。结束一次执行不等于完成任务。上述约束由跨模块用例统一落实，不能靠前端按钮禁用保证。

### 4.3 通知与后台管理的职责分界

通知负责提示和投递状态；目标进度是否达到完成条件、收到旧通知后是否仍允许结束，统一由目标模块判断。用户确认通知时，调用目标结束用例。

后台管理是受限管理入口。角色固定为普通用户、管理员、超级管理员；管理员不能借管理入口读取普通用户的目标、任务或习惯正文。账户修改交给身份模块执行，系统配置只包含已经约定的两项。

## 5. 公共工程支撑与跨模块协作

| 支撑能力 | 提供什么 | 业务责任仍属于谁 |
|---|---|---|
| 身份入口与通用校验 | 取得当前账户、参数校验、统一拒绝未授权请求 | 对象归属、父子关系和状态资格由用例与所属模块共同校验 |
| 事务、并发与幂等 | 原子提交、冲突处理、重复请求控制 | 需要原子完成的业务动作及冲突文案由具体用例定义 |
| 时间与后台调度 | 可测试的时间来源、到期触发和失败重试机制 | 目标启动延期、计划到期、失联暂停、习惯结算分别归所属业务模块 |
| 事件与通知投递 | 持久化重试依据、去重和处理记录的技术机制 | 事件含义与触发条件由业务定义；通知模块负责送达 |
| 日志、审计与观测 | 请求追踪、错误、性能、敏感操作审计 | 任务完成、专注区间、规则变更等业务历史由所属模块长期保存 |
| 数据库变更与交付 | 版本化迁移、环境配置、备份恢复和发布验证 | 数据含义和保留策略由业务与数据库设计确定 |

以下操作必须在架构阶段说明协调者、事务边界和失败结果：

| 用例 | 参与模块 | 协作结果 |
|---|---|---|
| 开始或切换任务 | 身份、目标与任务、计划、执行 | 校验资格；原运行任务暂停；新任务开始或恢复；保持计时唯一 |
| 任务改期 | 目标与任务、计划、执行 | 当前安排迁移；必要时暂停；不保留旧安排副本，不移动真实发生的投入 |
| 完成任务 | 目标与任务、执行、计划、通知 | 结束未结束执行、保存不可逆完成事实、更新当前进度；必要时可靠产生目标确认通知 |
| 目标归档或结束 | 目标与任务、执行、计划、通知 | 归档遇未结束执行时拒绝；主动结束先结束相关执行并由用户确认；撤出有效安排，保留历史，不伪造子任务完成 |
| 修改时区或撤销账户 | 身份、执行、计划、习惯 | 依业务要求暂停执行、撤销会话或记录生效节点；历史不按新时区重排 |
| 读取今日看板 | 相关业务模块、看板与统计 | 入口先协调必要的到期补偿，再读取已统一的状态；统计模块不随意改其他模块数据 |

本节定义业务协作要求。内部调用方式、事件存储方式和数据库锁方案在系统架构及数据库设计中确定。

### 6.1 数据访问方案比较与决策依据

| 方案 | 本项目的适配情况 | 主要代价 | 结论 |
|---|---|---|---|
| MyBatis | 显式 SQL、动态筛选、统计与结果映射符合任务、计划、历史查询特点 | 维护 Mapper 与 SQL 的对应关系，复杂 SQL 仍须评审 | 已采用，使用 XML 映射 |
| Spring JDBC | 同样支持手写 SQL、参数绑定、事务与 PostgreSQL 特性 | 复杂条件与结果映射较多时，需要自行组织重复代码 | 已评估，V1 业务持久层不采用 |

MyBatis 与 JDBC 都能正确实现行锁和事务；计时一致性取决于业务事务、并发控制与数据库约束，不能归功于某个持久层框架。MyBatis 的动态 SQL 与 Spring 事务集成有官方说明。[动态 SQL](https://mybatis.org/mybatis-3/dynamic-sql.html)、[Spring 事务集成](https://mybatis.org/spring/transactions.html)、[Spring JDBC](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html)

### 6.4 MyBatis XML 映射约定

以下为本项目后续代码结构和实现必须遵循的约定：

1. **SQL 与结果映射统一使用 XML。** 查询、插入、更新、删除和动态条件写在 Mapper XML 中，Java Mapper 接口负责声明方法签名。
2. **不采用注解映射。** 不使用 `@Select`、`@Insert`、`@Update`、`@Delete`、各类 SQL Provider 注解或 `@Results`、`@Result` 等结果映射注解；不将 SQL 移入 Java 字符串或 Provider 类绕过本约定。
3. **接口与 XML 明确对应。** 同名 Mapper 接口与 XML 文件一一对应；XML 的 `namespace` 使用接口完整限定名，语句 `id` 对应接口方法名，映射方法不重载。
4. **映射关系清晰可查。** 对业务对象和组合查询结果采用明确的 `resultMap`；计数、布尔值等标量结果可使用 `resultType`。同一查询不同时配置两者。
5. **参数绑定明确。** 业务值使用 `#{}` 绑定；多项条件优先封装为专用参数对象。排序字段和方向通过服务端白名单及 XML 分支选择，不将用户输入直接放入 `${}` 拼接 SQL。
6. **动态 SQL 留在 XML。** 使用 XML 的条件、集合及复用片段组织查询；账户归属、父子关系、状态和并发条件须在相应语句中明确落实。
7. **扫描与资源加载统一配置。** 统一注册 Mapper 接口，不逐接口添加 `@Mapper`；XML 路径和打包检查在代码结构阶段确定，确保正式产物包含所有映射文件。
8. **事务由应用用例负责。** Mapper 不承担跨模块业务编排，XML 不代替事务边界、业务校验或 PostgreSQL 约束；数据库结构变更仍由 Flyway 迁移文件管理。

这里的“不使用注解方式”指 MyBatis 的 SQL 和结果映射方式；Spring 的组件注册、事务和参数校验注解可按相应设计使用。统一 Mapper 扫描属于注册配置，具体配置方式在代码结构阶段给出。

上述 XML 元素、结果映射及参数绑定能力可参见 [MyBatis Mapper XML](https://mybatis.org/mybatis-3/sqlmap-xml.html)、[XML 动态 SQL](https://mybatis.org/mybatis-3/dynamic-sql.html)；Mapper 注册与资源加载参见 [MyBatis-Spring Mapper 注册](https://mybatis.org/spring/mappers.html)。

## 7. 需求对选型与后续设计的要求

| 业务或质量要求 | 对技术设计的直接要求 | 后续验证重点 |
|---|---|---|
| 同账户唯一运行任务、切换自动暂停 | 服务端统一协调，可靠事务和并发控制 | 两设备同时操作、重复提交、迟到请求 |
| 正向计时、强制退出后暂停 | 保存可信执行事实，区分实时估计和已确认值 | 断网、冻结、休眠、服务重启及跨日 |
| 周日计划唯一、过去只读、改期不留旧安排 | 持久层唯一性、服务端资格与历史事实分离 | 并发建计划、过期提交、执行中改期 |
| 删除不抹历史、习惯变更当天生效 | 生命周期、历史归属及规则版本有明确模型 | 删除后统计、当天完成后改规则、历史不重算 |
| 改密与账户撤销、普通用户数据隔离 | 成熟身份组件、对象归属校验、可撤销授权 | 横向越权、角色变化、旧会话继续请求 |
| 完成通知可靠且去重 | 业务成功与送达失败分别处理，有持久重试依据 | 投递失败恢复、重复事件、旧通知确认 |
| 备份与恢复、响应时间和容量 | 需要实际环境及数据规模验证 | 按 NFR 记录实测结果，不能预先写“满足全部要求” |

目前缺少引入 Redis、消息中间件、微服务或独立向量数据库的具体业务与规模依据。已有远程服务器安装pgvector 0.8.7仅作为环境事实登记；V1不启用vector扩展或向量业务，后续AI接入仍需具体用例与单独设计。

## 8. 开发顺序与阶段交付物

| 顺序 | 阶段 | 应形成的结果 | 进入下一步的条件 |
|---|---|---|---|
| 1 | 模块划分与技术选型 | 本文：模块职责、数据归属、协作要求、技术比较、XML 约定及兼容性依据 | 已于 2026-10-17 确认，作为后续设计输入 |
| 2 | 系统架构设计 | 前后端协作、部署单元、模块依赖、事务与事件、计时与调度、安全和故障恢复方案 | 核心跨模块流程有明确协调者，能够据此建模 |
| 3 | 数据模型与数据库设计 | 复核逻辑模型和数据字典；完成 ER、字段、类型、主外键、约束、索引、删除保留策略、3NF 分析及迁移设计 | 全范围业务数据与关键不变量覆盖，建表方案可评审 |
| 4 | 接口设计 | 请求方法、路径、参数、DTO/VO、权限、状态前提、数据去向、幂等、错误与分页契约 | 核心用例和异常有完整契约，前端所需数据可获得 |
| 5 | 代码结构与实施计划 | 工程与包结构、分层职责、模块调用约束、公共能力、配置和测试目录、模块实现顺序 | 设计可分批落实，依赖与每批验收条件明确 |
| 6 | 后端实现与接口验证 | 按契约逐模块实现、数据库迁移及必要自动化测试，接口调试记录 | 对应业务链路可真实持久化，异常、权限与并发路径通过验证 |
| 7 | 前端页面原型 | 根据业务与已设计 API 明确页面布局、字段、交互及加载、空、失败、冲突状态 | 主要操作与 API 对应，缺口通过变更回写契约 |
| 8 | 前端实现与联调 | 按原型和 API 实现页面，逐业务链路联调 | 页面操作、服务端状态与历史统计一致 |
| 9 | 系统验收与发布准备 | 功能验收、受影响的非功能验证、完整发布验证、迁移与恢复报告 | 采用的发布门槛通过，未通过项有明确处理结果 |

此顺序用于控制阶段产物。发现设计缺口时允许带着问题回修前一阶段，并记录影响；不要求等全部后端写完后才发现首个页面无法使用。原型正式制作仍按用户指定顺序，在后端阶段之后开展。

## 9. 技术决定与变更约束

前端采用Vue 3 + TypeScript，后端采用JDK 17、Maven 3.9.4和Spring Boot 3.5.16，数据库采用远程PostgreSQL 17.11；业务持久层使用Mapper接口及MyBatis XML。8个业务模块及公共工程支撑遵循第3～5章的职责边界，组件职责遵循第6章，精确版本遵循12。

数据库字段与约束以[01数据库设计与完整数据字典](../01-数据库设计与完整数据字典.md)为唯一现行基线；详细接口、工程与验收计划从[项目文档入口](../README.md)查阅。

方案变更应记录受影响的需求、模块、数据、接口与验证方法；不得在实现时静默改用注解SQL、其他持久层或其他Java主版本。
