## 三、本轮逐步开发记录：第 1---22 步

> 以下步骤按对话中逐步指导和反馈的顺序整理。不同步骤有不同目标，不能简单合并成"完成了异常处理"。

## 第 1 步：确认并完善 `ApiResponse<T>`

**文件：**
`app/src/main/java/com/asterway/app/web/contract/ApiResponse.java`

建立统一 HTTP 响应的基础结构，使用 Java `record`，包含四个字段：

-   `code`
-   `message`
-   `data`
-   `traceId`

随后修正了 `sucess` 的拼写问题，统一成功编码为
`"OK"`，并保留以下响应构造能力：

-   成功并返回业务数据。
-   成功但不返回业务数据。
-   失败并返回错误编码和提示。

### 本步涉及的 Java 知识

`record` 适合表达以数据为主的不可变对象。泛型 `ApiResponse<T>` 允许
`data` 保存不同类型的业务数据，同时保留编译期类型检查。

例如，`ApiResponse<UserView>` 表示返回用户视图，`ApiResponse<Void>`
表示不返回业务数据。静态泛型方法中的 `<T>`
是声明方法自己的类型参数，`ApiResponse<T>` 则是返回类型。

**完成状态：** 用户已编写并持续使用该 `record`，后续测试也基于它开展。

## 第 2 步：创建 `Violation`

**文件：**
`app/src/main/java/com/asterway/app/web/contract/Violation.java`

建立单条字段校验错误的数据结构，包含：

-   `field`：出错的字段名。
-   `message`：该字段的校验提示。

例如用户名为空时，可以返回 `field = "username"`
和相应提示，而不是只返回一个没有定位信息的通用错误。

**完成状态：** 后续字段校验处理器与测试使用了该类型。

## 第 3 步：创建 `ErrorData`

**文件：**
`app/src/main/java/com/asterway/app/web/contract/ErrorData.java`

建立用于承载错误附加数据的 `record`，其中包含
`List<Violation> violations`。

这三个类型的关系是：

-   `Violation` 表示一条字段错误。
-   `ErrorData` 表示一组校验错误。
-   `ApiResponse<ErrorData>` 表示统一响应中携带错误列表。

将它们放在 `app/web/contract`，是因为它们属于当前 HTTP
响应契约，而不是与 HTTP 无关的公共业务错误模型。

**完成状态：** 后续 `ApiErrorFactory.validationError(...)`
和字段校验测试使用了这些类型。

## 第 4 步：扩展 `ApiResponse.failure(...)`

为统一失败响应增加支持附加数据的能力，以便字段校验错误可以放进
`data`，而不必另建一套外层 JSON 结构。

目标调用形式是：

``` java
ApiResponse.<ErrorData>failure(
        "VALIDATION_ERROR",
        "请检查填写内容",
        errorData,
        traceId
);
```

这里的泛型参数表示失败响应的 `data` 类型为
`ErrorData`。该设计保留统一外壳，同时允许失败场景返回字段错误列表。

**完成状态：** 后续 `ApiErrorFactory.validationError(...)`
使用了带错误附加数据的失败响应构造方式。

## 第 5 步：创建 `ErrorCode` 接口

**文件：**
`common/src/main/java/com/asterway/common/error/ErrorCode.java`

定义公共错误码契约，要求实现类型提供：

-   `code()`
-   `message()`

该接口只描述"错误码需要提供哪些信息"，不直接依赖 HTTP 状态码或 Spring
MVC。

**设计意义：** 公共模块可以表达业务错误，而 HTTP 状态映射由应用 Web
层负责，降低公共业务代码对 Web 框架的耦合。

## 第 6 步：创建 `CommonErrorCode`

**文件：**
`common/src/main/java/com/asterway/common/error/CommonErrorCode.java`

建立公共错误码枚举，实现 `ErrorCode`。本轮涉及的错误包括：

-   `VALIDATION_ERROR`
-   `AUTH_REQUIRED`
-   `FORBIDDEN`
-   `NOT_FOUND`

每个枚举值包含机器可识别的错误编码和默认提示。

开发过程中，用户贴出的代码包含一条与错误码无关的
`EmbeddedLdapProperties`
导入。它不属于该枚举的职责，应移除，避免引入无用依赖。

**完成状态：** 用户明确反馈已实现，后续业务异常和测试使用了
`CommonErrorCode.NOT_FOUND`。

## 第 7 步：创建 `BusinessException`

**文件：**
`common/src/main/java/com/asterway/common/exception/BusinessException.java`

建立公共业务异常，用来携带结构化的
`ErrorCode`，而不是依赖解析任意异常文本来判断业务失败类型。

其用途是让业务代码可以表达类似"资源不存在"的业务事实，再由 Web
层统一转换成 HTTP 响应。

**职责边界：** `BusinessException` 负责表达业务错误；它本身不负责写 HTTP
JSON，也不负责决定 MVC 响应头。

**完成状态：** 后续 `ApiErrorFactory` 和 `ApiErrorContractTest`
均使用该类。

## 第 8 步：创建 `ApiErrorFactory`

**文件：**
`app/src/main/java/com/asterway/app/web/error/ApiErrorFactory.java`

将错误信息转换成 HTTP 状态码和
`ApiResponse`。当前已经验证或使用的映射包括：

  场景                 HTTP 状态 响应错误码
  ------------------ ----------- --------------------
  需要认证                   401 `AUTH_REQUIRED`
  无权执行                   403 `FORBIDDEN`
  资源不存在                 404 `NOT_FOUND`
  未知内部异常               500 `INTERNAL_ERROR`
  字段业务校验失败           422 `VALIDATION_ERROR`

字段校验方法是在后续第 20 步补充的，不能将它误记为一开始就全部实现。

**职责意义：** 集中维护状态码与响应体映射，避免每个 Controller
重复构造错误 JSON。

## 第 9 步：创建 `GlobalExceptionHandler`

**文件：**
`app/src/main/java/com/asterway/app/web/error/GlobalExceptionHandler.java`

建立全局 MVC 异常处理入口。它负责捕获异常，并把响应构造工作交给
`ApiErrorFactory`。

随着后续步骤推进，它逐步覆盖：

1.  `BusinessException`。
2.  未知 `Exception`。
3.  `MethodArgumentNotValidException` 字段校验异常。

第三种处理是在第 21 步添加的，并不是最初创建类时就已完成。

**职责意义：** Controller 不必在每个方法中重复写
`try/catch`，也不必重复拼接错误 JSON。

## 第 10 步：第一次执行 Maven 编译

完成公共错误契约、业务异常、错误工厂和全局异常处理的基础实现后，执行
Maven 根工程的 `compile`。

目的不是验证业务逻辑是否完全正确，而是先检查：

-   多模块依赖是否能够解析。
-   包名与类名是否一致。
-   方法签名是否匹配。
-   Java 类型是否能通过编译。

**完成状态：**
用户反馈构建成功。之后仍继续扩展请求追踪、响应序列化与测试，因此这次编译不等于整个功能开发结束。

## 第 11 步：创建 `TraceIdFilter`

**文件：**
`app/src/main/java/com/asterway/app/web/filter/TraceIdFilter.java`

建立请求追踪过滤器，主要负责：

1.  为请求生成追踪标识。
2.  将标识保存到当前请求属性中。
3.  通过 `X-Trace-Id` 响应头返回标识。
4.  将标识放进 MDC 日志上下文。
5.  在请求处理结束时清理或恢复 MDC，避免线程复用导致上下文串线。

**完成状态：** 用户反馈编译成功。后续 MockMvc
测试验证了响应头与响应体中的追踪标识一致。

## 第 12 步：为失败响应增加 `traceId` 传递能力

在 `ApiResponse` 的基础上增加可携带 `traceId` 的失败响应构造方式。

目标是避免异常响应只能输出错误码与提示，却无法关联到产生该响应的请求。

例如，同一个请求的响应头可能是：

``` text
X-Trace-Id: 4c2...
```

JSON 响应体中的 `traceId` 也应当是同一个值。

**完成状态：** 用户反馈该步骤成功，后续异常链路测试验证了这一约定。

## 第 13 步：将 `traceId` 串入错误处理链

调整 `GlobalExceptionHandler` 与 `ApiErrorFactory`
的协作方式，使异常处理器从请求属性中取得 `traceId`，并传给错误响应工厂。

形成如下关系：

``` text
TraceIdFilter
    ↓ 设置 request attribute
GlobalExceptionHandler
    ↓ 读取 traceId
ApiErrorFactory
    ↓ 生成统一错误响应
ApiResponse
```

**完成状态：** 用户反馈 Maven 编译成功。后续 MockMvc
测试确认请求追踪标识在响应头和 JSON 中一致。

## 第 14 步：为成功响应增加 `traceId` 构造方法

发现成功响应工厂方法最初把 `traceId` 固定为
`null`，因此增加了可由调用方传入追踪标识的成功响应方法。

本步骤区分：

-   `success(data)`：兼容普通成功调用。
-   `success(data, traceId)`：成功并返回业务数据，同时携带追踪标识。
-   `successWithTraceId(traceId)`：成功但不返回业务数据，同时携带追踪标识。

这里要注意：**增加方法只代表具备这种构造能力，不代表所有成功接口已经自动注入了
`traceId`。** 后续仍需要在真实响应链路中统一使用它，或通过合适的 Web
层机制自动填充。

## 第 15 步：保证 `ApiResponse` 中的 `null` 字段参与 JSON 序列化

## 第 20 步：为字段校验错误扩展 `ApiErrorFactory`

在 `ApiErrorFactory` 中新增 `validationError(...)`，接收
`List<Violation>` 和 `traceId`，把它们包装进 `ErrorData`，再通过
`ApiResponse<ErrorData>` 返回。

本步骤确定字段业务校验失败的响应约定：

-   HTTP 422。
-   `code = "VALIDATION_ERROR"`。
-   `message = "请检查填写内容"`。
-   `data.violations` 保存字段错误列表。
-   `traceId` 保存当前请求标识。

接口规范还区分 JSON 解析错误等 HTTP 400
场景。本步骤只实现业务字段校验失败的 422 响应，不等于 400
解析异常已经实现。

**完成状态：** 用户反馈 Maven 构建成功。

## 第 21 步：在 `GlobalExceptionHandler` 中处理字段校验异常

新增对 `MethodArgumentNotValidException` 的处理：

1.  从异常的 `BindingResult` 中读取字段错误。
2.  遍历 `FieldError`。
3.  将每个错误转换为 `Violation(field, message)`。
4.  调用 `ApiErrorFactory.validationError(...)` 生成统一响应。

这一步将 Spring MVC 的参数校验异常接入此前建立的统一错误处理链。

**完成状态：** 用户反馈编译成功。

## 第 22 步：测试字段校验异常的完整 MVC 链路，并修正测试代码

在 `ApiErrorContractTest` 中增加字段校验测试，使用测试专用 DTO：

``` java
record ValidationRequest(
        @NotBlank(message = "用户名不能为空")
        String username,
        @NotBlank(message = "昵称不能为空")

```

在测试 Controller 中通过 `@Valid @RequestBody` 接收请求，并对
`/test/validation` 发送包含两个空字符串的 JSON。

测试检查：

-   `VALIDATION_ERROR`。

### 主要调用链

``` text
HTTP 请求
   ↓
TraceIdFilter
   ├── 生成 traceId
   ├── 设置请求属性
   ├── 设置 X-Trace-Id 响应头
   └── 写入 MDC
   ↓
Spring MVC Controller
   ├── 业务异常 ──────────────┐
   ├── 参数校验异常 ──────────┤
   └── 未知异常 ──────────────┤
                             ↓
                  GlobalExceptionHandler
                             ↓
                      ApiErrorFactory
                             ↓
                         ApiResponse
```

### 模块边界

-   `common/error`：错误码公共契约。
-   `common/exception`：公共业务异常。
-   `app/web/contract`：HTTP 响应契约与校验错误数据。
-   `app/web/error`：HTTP 错误映射与全局异常处理。
-   `app/web/filter`：请求追踪等 Web 过滤能力。

这种拆分使公共业务错误不必依赖 HTTP，而应用层负责把它转换成具体状态码与
JSON。
